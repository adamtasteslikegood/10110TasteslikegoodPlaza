# Bridge Protocol

WebSocket on `ws://localhost:8765` (D-015). JSON messages, one per WebSocket frame.

## Current prototype scope

The request/response examples below describe the current implementation, not a
durable platform API. NPC conversation history is connection-local; domain SDK
clients, lifecycle state, and output buffers are bridge-process-local. Neither
engine currently provides bridge-managed recovery after a bridge restart.

The shipped Godot client sends plain conversation requests only. Domain routing,
lifecycle commands, and output replay exist in the bridge but are not yet wired
into that client. The bridge remains unaware of rendering and controls (D-005);
see the [platform design's client requirements](../docs/superpowers/specs/2026-10-18-bridge-first-platform-design.md).

Future work is separated under [Planned platform evolution](#planned-platform-evolution).
That section adds no implemented fields, commands, or persistence guarantees.

## Request Types

### Conversation (backward-compatible with M8)

```json
{
  "type": "conversation",
  "agent_id": "security-auditor",
  "task": "What's your take on the new hire?",
  "request_id": "optional-uuid"
}
```

A request **without** a `type` field is treated as `"conversation"` — existing
clients work without changes.

`request_id` is accepted in a conversation request, but current conversation
success and error responses do **not** echo it. Chat correlation is planned for
M11; clients cannot rely on it today.

#### Conversation history

The bridge remembers a conversation for as long as the WebSocket connection it
arrived on stays open. Within a connection it keeps one history per `agent_id`:
each successful exchange is appended, and the next request for that agent is
sent to the model with those earlier turns in front of it.

- **The client sends nothing extra.** There is no conversation id and no
  history field. A client holds a conversation by keeping its connection open
  and loses it by reconnecting. Any client gets this the same way (`D-005`).
- **A new connection starts with nothing**, and two connections never see each
  other's turns, even for the same agent.
- **Only successful exchanges are kept.** A request that fails, or a reply with
  no text, leaves the history as it was, so retrying does not repeat the
  question.
- **It is bounded.** The newest 40 messages (20 exchanges) per agent are kept;
  older ones are dropped whole, oldest first.
- **It is not persisted.** Nothing is written to disk, and a bridge restart
  forgets everything. There is no stable conversation identity for reconnect or
  restart recovery. Durable session state is planned for M13.

### Domain Query

```json
{
  "type": "domain_query",
  "domain_id": "engineering",
  "agent_id": "systems-architect",
  "task": "Review the auth middleware",
  "request_id": "uuid"
}
```

Domain queries run asynchronously. The response arrives as a push message
when the Agent SDK completes. If the domain is backgrounded, output
accumulates in the buffer for later resume.

Successful domain output already carries the query's `request_id` (generated by
the bridge if omitted) and an `output_id`. These fields predate the planned M11
conversation correlation work. The current `domain_id` selects a process-local
session; it is not a user/project namespace or an authorization boundary.

### Resume

```json
{
  "type": "resume",
  "domain_id": "engineering",
  "cursor": "last-seen-output-id"
}
```

Returns all output entries since the cursor. Also refocuses the domain
(transitions from BACKGROUNDED to ACTIVE).

This is output replay from the current in-memory buffer, not persistent SDK
session recovery. `output_id` is a monotonically increasing integer serialized
as a string, scoped to that domain session's buffer. A cursor selects entries
with a greater ID; an omitted or nonnumeric cursor replays the whole buffer.
IDs and cursors have no durability guarantee across session replacement or a
bridge restart. No SDK recovery is established by the existing internal session
ID alone.

### Lifecycle Commands

```json
{"type": "activate_domain", "domain_id": "engineering"}
{"type": "background_domain", "domain_id": "engineering"}
{"type": "refocus_domain", "domain_id": "engineering"}
{"type": "deactivate_domain", "domain_id": "engineering"}
```

## Response Format

Both engines return `agent_id`, `task`, `output`, and `status`. Successful domain
output adds `domain_id`, `request_id`, and `output_id`, as shown here; current
conversation replies omit those three fields:

```json
{
  "agent_id": "systems-architect",
  "task": "Review the auth middleware",
  "output": "Looking at the middleware...",
  "status": "ok",
  "domain_id": "engineering",
  "request_id": "uuid",
  "output_id": "0"
}
```

Error responses add `error_type` and `message`:

```json
{
  "agent_id": "systems-architect",
  "task": "Review the auth middleware",
  "output": "",
  "status": "error",
  "error_type": "not_found",
  "message": "No agent 'systems-architect'"
}
```

### Error types

| error_type | Meaning |
|---|---|
| `timeout` | Claude API call exceeded the timeout (D-006) |
| `auth` | No valid credentials found |
| `not_found` | agent_id not in the agent store |
| `api_error` | Claude API returned an error |
| `invalid_request` | Malformed JSON or missing required fields |

## Domain State Notifications (push)

Sent by the bridge when domain state changes:

```json
{
  "type": "domain_state",
  "domain_id": "engineering",
  "state": "backgrounded",
  "unread_count": 3
}
```

## Domain Session States

```
INACTIVE → ACTIVATING → ACTIVE → BACKGROUNDED → ACTIVE (refocus)
                          ↓           ↓
                     DEACTIVATED  DEACTIVATED
```

## Planned platform evolution

The following milestones are **planned, not implemented by this document**.
Sequencing and acceptance criteria live in the [roadmap](../specs/roadmap.md);
the [bridge-first platform design](../docs/superpowers/specs/2026-10-18-bridge-first-platform-design.md)
describes the intended boundaries and open contract decisions.

| Milestone | Intended change |
|---|---|
| M10 | Local configuration, JSONL transcripts, and operational logs. These records aid inspection and diagnosis; they are not authoritative durable session state or proof that SDK execution can resume. |
| M11 | Echo and correlate conversation `request_id` values, including failure handling. Successful domain output already includes request/output IDs as documented above. |
| M12 | Wire the client to domain lifecycle and output replay. Presentation and controls remain client concerns. |
| M13 | Durable identities scoped by user, project, and domain, with defined restart/reconnect recovery. Exact fields and recovery semantics require implementation and verification. |
| M14 | Worktree isolation and ownership for domain execution. The current placeholders do not implement isolation. |
| M15 | Authenticated hosted operation with durable storage and enforced ownership/access boundaries. |

Future user/project labels are intended identity inputs, not trusted principals
or authentication in today's local protocol. Transcripts, logs, labels, and an
SDK session ID do not independently establish durable ownership or recovery.
